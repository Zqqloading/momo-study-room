# Agent 工具调用基础

## 一、工具调用是什么

大模型本身只会生成文本，不能查数据库、不能读文件、不能发请求。工具调用（tool calling / function calling）
是给模型一份工具清单，每项写明名字、用途和参数格式；模型在回答前可以决定先调用其中某个工具，
拿到结果再继续。工具执行由程序完成，模型只负责选择工具和组织参数。

一个常见的误解是"模型自己执行了工具"。实际链路是：

1. 程序把工具清单和对话交给模型；
2. 模型返回一个工具调用请求（工具名 + 参数）；
3. 程序校验参数、执行工具、把结果写回对话；
4. 模型基于结果继续，或直接给出最终回答。

所以工具的安全性、次数上限、失败处理都在程序侧，不在模型侧。

## 二、有界回合

如果允许模型无限次调用工具，成本和延迟都不可控：一次循环可能触发几十次检索，用户等不到回答。
有界回合给每轮对话设三条上限：

- 工具调用总次数（例如每回合 8 次）；
- 单个工具的次数上限（例如网页搜索 4 次）；
- 单回合总耗时（例如 60 秒）。

到达任一上限就停止调用，用已有信息回答，并说明"没查完"。上限存在的意义不是省钱，
而是让"什么时候停"这件事可预测；没有上限的 agent 在真实故障下会一直重试。

## 三、程序工具与 agent 工具

工具按"谁对结果负责"分两类：

- **程序工具**：出题、评分、写库、结算。结果由程序产生，agent 不能改写；
- **agent 工具**：检索、搜索、换说法再查。agent 决定查什么、查几次，并对如何组织语言负责。

混用会造成两类事故：让 agent 复述评分结果，分数可能被改写成别的数字；让 agent 直接写库，
业务流程绕过校验。判断标准是：这个动作的结果要不要被审计、被计分、被回放。要，就归程序。

## 四、失败处理

工具失败是常态：超时、限流、参数非法、返回空结果。三条约定：

1. 失败也算一次调用，计入上限，否则重试会无限膨胀；
2. 失败要作为观察结果回给模型，让它决定换工具还是放弃；
3. 被上限拦下的调用不算失败，也不计入次数，否则日志会把"没调用"记成"调用失败"。

## 五、常见坑

- 把工具描述写成营销文案，模型看不出参数边界，调用参数经常缺失；
- 工具返回整页 HTML，模型被噪声淹没，回答开始编造；
- 不区分"没查到"和"查到了空结果"，两者对用户的含义完全不同；
- 工具清单随版本变化但没写进契约，线上行为和测试环境不一致。
