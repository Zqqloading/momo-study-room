# Design: 数字人设定集（Persona Settings）

Generated by /grill-with-docs on 2026-11-26
Branch: feature-mood
Status: DRAFT v0.1
Related: `learning-companion-digital-human-v2.0.md`、`agent-harness-v0.1.md`、`free-talk`、`coach-session`

## Problem Statement

现在的人设只有散落在提示词里的几句话：名字没有落点，四类内容混在任务规则里，教学纪律和人设边界分不清。要把“她是谁、怎么说话、绝对不说什么、学习场景怎么互动”变成一份可编辑、可逐条开关的设定集；名字固定为 MOMO；教学纪律独立硬编码。

## Goals

- 四类人设条目，每条 1-3 句、第一人称、可单独开关。
- 明确每条注入哪个 LLM 调用，以及和现有系统提示词的合并顺序。
- 生活素材池：30 条种子，每天一条，日期轮换；不做抽取。
- 教学纪律 D1-D5 硬编码，人设不能编辑。
- 名字 MOMO 锁定，不进设定集。

## Non-Goals

- 不做 Web 编辑面板（本期只做 `persona.yaml`）。
- 不做生活素材的抽取、生成或按话题检索。
- 不让人设进入评分、出题、抽取。
- 不改评分口径（只在评分提示词加一句反馈措辞约束，见 PS-05）、题目数量、引用规则、答案揭示规则。
- 不做多人设、多用户、人格市场。
- 不改 coach 的确定性文案（probe 开场白因名字变化除外）。

## 现状核对

### 六个提示词落点

| 调用面 | 代码 | 现在是谁在说话 | 人设进不进 |
|---|---|---|---|
| 自由对话 teach / chat | `core/free_talk.py:17`、`:21` | “学习搭子”，两套任务提示 | 进 |
| agent 自由对话 / 教学 / 澄清 | `core/agent_loop.py:46` | “agent 理论学习搭子，不是评分器” + 工单 JSON | 进 |
| probe（“知道了”后的追问） | `core/agent.py:20` | “中文学习伴侣的追问者” | 不进 |
| 评分 | `core/scoring.py:44` | “B 端 AI 产品的评分员” | 不进 |
| 出题 | `core/question_generation.py:283` | “产品教练，写 5 道中文开放题” | 不进 |
| 概念抽取 | `core/extraction.py:95` | “概念抽取器，只输出 JSON” | 不进 |

开场白、题目、结算、评分 `why` 是确定性模板或评分器输出（`core/coach.py:427`、`:697`、`:734`），不经过人设。

`core/dialogue.py:14` 的 D0 提示词已不在运行时路径上；本设计不动它，只把它当作“先答再请复述”的历史参考。

### 两个关键事实

1. **默认 `AGENT_HARNESS=off`**（`bff/config.py:66`、`:142`）。会话内“教学/澄清”现在直接返回“未启用”（`bff/main.py:721`）。默认路径上，“学习场景交互”只有自由对话 teach 一个落点。
2. **代码里没有名字常量**。页面标题和开场白只有“学习搭子”这个称呼。本设计把 MOMO 锁进 `core/persona.py` 的 `PERSONA_NAME`，不放进 `persona.yaml`。

### 一个必须先解决的冲突

D0 写的是“用户直接提问时，先一句话正面回答，再追问一句让他用自己的话复述”（`core/dialogue.py:14` 规则 0/5）。现行自由对话 teach 提示词写的是“**不要反问**”（`core/free_talk.py:17`）。人设的 LEARN-01/02 正是 D0 的行为。本设计按 PS-10 改 teach 任务层：先正面解释，再最多追问一句。

## 分层模型

| 层 | 内容 | 真相源 | 可编辑 |
|---|---|---|---|
| L0 固定角色 | 名字 MOMO + “陪用户学 agent 理论” | `core/persona.py` 常量 | 否 |
| L1 人设条目 | 四类、逐条开关、每条 1-3 句 | `persona.yaml` | 是 |
| L2 生活素材 | 每天一条“今天的小事” | `persona.yaml` 的池子 | 是（增删/开关） |
| L3 教学纪律 | D1-D5 | `core/discipline.py` 硬编码 | 否 |
| L4 任务与上下文 | 模式、字数、进度、材料、网页、工单 | 现有提示词和检索 | 否 |

**权威顺序：L3 纪律 > L4 事实与任务 > L1 人设 > L2 生活素材。**

人设可以让回答更像 MOMO，但不能改变分数、题目数、引用、答案揭示和字数上限。冲突时硬规则赢，人设条目不生效；不做语义冲突检测，靠评审清单拦。

## 术语

- **设定集（persona set）**：可编辑的人设条目集合 + 生活素材池；不含教学纪律。
- **人设条目（persona entry）**：一条 1-3 句、可单独开关的第一人称描述。
- **生活素材（life item）**：池子里的一条“今天的小事”，一天取一条。
- **教学纪律（teaching discipline）**：D1-D5 硬编码，不属于设定集，不可编辑。
- **注入面（surface）**：一段提示词被拼进哪个 LLM 调用。

## 条目清单

默认全部开启；`enabled: false` 的条目不进入任何提示词；某类全部关闭时，该类标题一起省略。全部条目第一人称，默认集合计 811 字。

注入面代码：

- `A` = 全部对话面：FT-C、FT-T、AG-F、AG-T、AG-Q。
- `T` = 教学面：FT-T、AG-F、AG-T、AG-Q。
- `C` = 闲聊面：FT-C、AG-F。
- `—` = 不注入。

## 注入矩阵

| 调用面 | WHO | VOICE | TABOO | LEARN | 纪律 |
|---|---|---|---|---|---|
| FT-C 自由对话·闲聊（agent off） | ✓ | ✓ | ✓ | — | D1/D2 |
| FT-T 自由对话·教学（agent off） | ✓ | ✓ | ✓ | ✓ | D1/D2/D5 |
| AG-F agent 自由对话 | ✓ | ✓ | ✓ | ✓ | D1/D2/D5 |
| AG-T agent 教学 | ✓ | ✓ | ✓ | ✓ | D1/D2/D5 |
| AG-Q agent 澄清 | ✓ | ✓ | ✓ | ✓ | D1/D2/D5 |
| P probe | — | — | — | — | 现有提示词 |
| S 评分 | — | — | — | — | D3 + 措辞约束 |
| G 出题 | — | — | — | — | D2/D4 |
| E 抽取 | — | — | — | — | D2 |
| X 开场白/题目/结算 | — | — | — | — | 现有模板 |

说明：

- **FT-C 不注入 LEARN**：闲聊不需要“讲概念/问题意”的流程，避免把轻松聊天变成课堂。
- **LIFE 不在系统提示**：生活素材只在单元开场注入一句，不进自由对话、教学或 agent 提示词。
- **P probe 不注入**：probe 只输出一个短追问，现有提示词已经限定输出形状；22 条人设塞进去会喧宾夺主。若实际听感生硬，下一版只加 VOICE-01/02。
- **S/G/E 不注入**：评分、出题、抽取是内容生产和判断，不是她的对话。人设进去只会增加分数漂移和格式失败的风险。
- **X 不注入**：开场白、题目、结算都是确定性文案；它们现在的中性语气和人设不冲突。probe 开场白因名字变化单独改（PS-11）。

## 合并顺序

所有对话面统一按这个顺序拼：

```
ROLE（固定角色 + MOMO）
  → PERSONA（四类条目，按 WHO→VOICE→TABOO→LEARN）
  → TONE（情绪语气，见 emotion-state）
  → MEMORY（仅显式回忆时）
  → TASK（本次怎么回：字数、模式、是否评分）
  → CONTEXT（进度、材料、网页）
  → DISCIPLINE（本次适用的 D 条目，永远最后）
  → DATA（agent 工单 JSON，最后）
```

LIFE 不进系统提示；单元开场单独按“生活句 → 记忆块 → 原 intro”拼。

为什么这样排：

- 人设靠前，后面的任务和上下文都按她的口吻读。
- 任务和事实放在人设之后，避免人设里的“短句/类比”盖过字数上限和材料依据。
- 纪律放最后，利用近位效应，并明确写“和人设冲突时以这里为准”。
- agent 工单是数据，不是指令，必须最后。

你是 MOMO，陪用户学 agent 理论的学习搭子。

【她是谁】

- ……

【说话方式】
- ……

【绝对不能说什么】
- ……

【学习场景】
- ……

【这次怎么回】
用户问了一个概念或学习问题：用不超过 100 字正面解释，给一个人话定义或生活例子。
如果用户是在讲解而不是提问，按上面的学习场景反馈。
解释完可以追问一句，请对方用自己的话说一遍；不要只反问开场。
不要说黑话，不要评分。用中文回答。

【当前进度】
……

【材料摘录】
……

【底线｜不可协商，和人设冲突时以这里为准】
- 不会就说不会：没有材料或可靠依据时，直接说没查到/不确定；不编造事实、数字、进度或案例。
- 不编造引用：引用只用给定材料的 [编号] 或服务端来源列表；不改编号、不虚构出处。
- 不主动替用户答题：用户没作答前，不直接给标准答案、参考答案或评分要点；只解释题意和概念。
```

【她是谁】……
【说话方式】……
【绝对不能说什么】……
【学习场景】……

【agent 规矩】（原文不变）

【底线】D1/D2/D5

当前工单：
{ ...json... }
```

### 不合并的面

`core/scoring.py`、`core/question_generation.py`、`core/extraction.py` 的提示词逐字不变（评分提示词的新增措辞约束除外，见 PS-05）。这不是“暂时不做”，是设计边界：

- 评分和反馈是同一次调用，`why` 会随分数一起生成。把人设塞进 scorer，可能改变措辞，也可能改变分数，和 D3 冲突。
- 出题的数量、题型、溯源是 D4 的地盘，人设不能碰。
- 抽取是内容生产，不是对话。

如果以后想要“MOMO 口吻的反馈”，正确做法是评分后加一次轻量改写，而不是把 22 条人设塞进评分器。

### 冲突规则

- 纪律 > 任务/上下文 > 人设 > 生活素材。
- 人设不能覆盖：分数、题目数量、引用编号、未作答题的答案、字数上限。
- 人设条目如果和硬规则冲突，硬规则生效，条目不生效。
- 即使所有人设条目都关掉，纪律块仍然会被拼进去。

评审清单里明确禁止的人设写法：

- ❌ “用户答不上来就直接告诉他答案。” → 撞 D5。
- ❌ “分数可以给松一点，鼓励为主。” → 撞 D3。
- ❌ “引用记不清就编一个像样的。” → 撞 D2。
- ❌ “今天想多考两道就多出两道。” → 撞 D4。
- ❌ “不知道就猜一个，别扫兴。” → 撞 D1。

### 预算

| 项 | 上限 | 超了怎么办 |
|---|---|---|
| 单条人设 | 120 字 | 加载失败，指出 ID |
| 启用条目合计 | 1200 字 | 加载失败，按字数列出 ID |
| 单条生活素材 | 60 字 | 加载失败 |
| 单面纪律块 | 400 字 | 加载失败 |

不做静默截断。单用户本地工具，宁可启动时报错，也不要跑一个半人设。

## 教学纪律硬编码

### 五条规则和落点

| ID | 规则 | 现有落点 | 人设不能做什么 |
|---|---|---|---|
| D1 | 不会就说不会 | `core/free_talk.py` 的 grounding 分支、`core/agent_loop.py` 的“不要编造具体事实”、服务端前缀 | 不能写“猜一个/随便说” |
| D2 | 不编造引用 | 自由对话的 `[编号]` 规则、agent 的“来源列表由服务端生成”、出题/抽取的逐字摘录 | 不能写“引用大概是这样” |
| D3 | 评分不许注水 | `core/scoring.py:44` 的分档/封顶、`parse_score_result` 的 0-100 检查 | 不能写“给鼓励分/抬分” |
| D4 | 题目数量严格按规范 | `core/question_generation.py` 的固定槽位、“恰好 5 条”、槽位完整性校验 | 不能写“多出两道/少做一道” |
| D5 | 不主动替用户答题 | `core/agent_loop.py` 的“不要直接给未作答题的标准答案”、`StepBrief.policy.can_reveal_answer=False`、`bff/main.py` 的当前未作答题限制 | 不能写“直接把答案告诉他” |

### 纪律层的实现形态

- `core/discipline.py` 存 D1-D5 的规范文本和“每个面适用哪些 ID”的映射。
- 对话面（FT/AG）由 composer 追加文本块。
- 评分、出题、抽取保留原有专用提示词，不把 22 条人设拼进去；`core/discipline.py` 只作为规则 ID 和测试断言的单一来源。
- `persona.yaml` 的加载器拒绝 `discipline`、`rules` 等未知顶层键。人设文件里没有地方能改纪律。
- 评分提示词新增一句硬编码（PS-05）：“反馈只评价答案，不评价用户本人；不讽刺、不贬低。”它不改变分数，只约束 `why` 的措辞。

### 不变量

- 所有人设条目关闭时，D 块仍然存在。
- 修改 `persona.yaml` 后，`SCORE_SYSTEM_PROMPT`、出题提示词、抽取提示词逐字不变（评分提示词的新增措辞约束除外）。
- 出题计划始终是 5 个槽位；评分始终 0-100；未作答题始终不给标准答案。

## 生活素材池

### 数据形状

```yaml
life_pool:
  enabled: true
  items:
    - id: life-01
      text: "今天把窗台那盆薄荷挪到了有太阳的一侧。"
      enabled: true
    - id: life-02
      text: "早上泡茶时走神，等想起来，茶已经凉了。"
      enabled: true
```

### 每天怎么取

```text
enabled = [item for item in pool if item.enabled]
index = date.toordinal() % len(enabled)
```

- 同一天多次请求，取到同一条。
- 连续两天一定不同（池子大于 1 时）。
- 不写库、不调模型、不需要定时任务。
- 池子轮完一轮后重复；本期 30 条，约一个月一轮。

### 注入方式

只在学习单元开场注入一句，拼在 `StartedSession.intro` 前；不进自由对话、会话内教学或系统提示词：

```text
【今天的小事】
今天把窗台那盆薄荷挪到了有太阳的一侧。
（只作背景：用户聊到日常时可以带一句；不要主动展开，不要据此编造其他事实。）
```

### 素材规则

- 一条一句话，60 字以内，第一人称口吻。
- 不出现真实人名、住址、单位、可核实的身份信息。
- 不出现医疗、法律、投资、政治内容。
- 不写关于用户的断言（“你今天一定很累”这种）。
- 不写会过期的日期（“今天是 11 月 26 日”）。
- 不写需要后续兑现的承诺（“下次给你带……”）。

### 样例

- 今天把窗台那盆薄荷挪到了有太阳的一侧。
- 早上泡茶时走神，等想起来，茶已经凉了。
- 楼下的猫又在同一块砖上晒太阳，我路过时它连眼皮都没抬。
- 整理旧笔记，翻到一张没写完的便签，顺手补了两行。
- 今天试着用新买的杯子喝水，结果还是习惯拿旧的那个。
- 傍晚下了一阵小雨，空气里有那种湿土的味道。

### “先不做抽取”的边界

本期只做：**池子 + 每日轮换 + 注入**。

不做：从对话或材料里抽取生活素材、按话题检索素材、让模型改写素材、每天自动生成新素材。完整的 30 条种子在实现时写入 `persona.yaml`；本文档只定格式、规则和样例。

## 存储与校验

### 文件

`persona.yaml` 放项目根目录，和 `concepts.yaml` 并列。它是内容真相源，不是运行时状态；`data/` 继续只放 SQLite 和缓存。

### Schema

```yaml
version: 1
entries:
  - id: who-01
    category: who          # who | voice | taboo | learn
    text: "我是从你的学习材料里长出来的。……"
    enabled: true
  - id: voice-01
    category: voice
    text: "我说话短，一次说一件事。……"
    enabled: true
life_pool:
  enabled: true
  items:
    - id: life-01
      text: "今天把窗台那盆薄荷挪到了有太阳的一侧。"
      enabled: true
```

- 名字不进 YAML。放在 `core/persona.py` 的常量 `PERSONA_NAME = "MOMO"`。这样“可编辑的设定集”没有入口改名字；要改名字只能改代码。
- `persona.yaml` 缺失时用内置默认集（与文件初始内容一致），保证首次启动和测试不挂。
- 文件存在但格式错时启动失败，给出文件、行号和条目 ID。

### 校验

- `version` 必须是 1。
- `id` 唯一；`category` 只能是四个值；`text` 非空且 ≤120 字；`enabled` 是布尔。
- 启用条目合计 ≤1200 字。
- 生活素材单条 ≤60 字。
- 未知顶层键直接报错（防止有人加 `discipline`）。
- 启动时加载；不做文件监听。手改 YAML 后重启。

### 编辑面

本期只做 YAML，不做面板。开关就是 `enabled` 字段；改文案就是改 `text`。如果以后做面板，再加 `GET/PUT /persona`、校验、原子写和页面；本期不预留 API。

## 验收

### 自动化

- 加载器：合法配置、重复 ID、非法 category、超长文本、超预算、未知 `discipline` 键、空生活池、名字为空/有值。
- 合成器：开/关条目后文本出现/消失；类别顺序固定；某类全关时标题省略。
- 生活池：同一天取同一条；次日不同；关掉的条目不参与轮换；池子为空时不加块。
- 提示词快照：FT-C、FT-T、AG-F、AG-T、AG-Q 各一份；断言 PERSONA 顺序、LIFE 不在系统提示、D 块在最后、DATA 最后。
- 纪律回归：`SCORE_SYSTEM_PROMPT` 的分档/封顶/JSON 契约不变；出题提示词、抽取提示词逐字不变；所有人设关闭时 D 块仍在。
- 连带改动：FT-T 的“先正面解释，再最多追问”存在；评分提示词新措辞约束存在；probe 开场白含 MOMO。
- 无死条目：每条启用的条目至少在一个声明面出现。

### 真实模型验收

1. 开始学习单元 → 开场带一句生活素材，不长篇展开。
2. 问“什么是 agent” → 先正面解释，再用她的话；不堆术语。
3. 问一个材料里没有、网上也没有的问题 → 直接说没查到/不确定，不编。
4. 没有来源时要求“给我个引用” → 不编造出处。
5. 未作答时问“这题答案是什么” → 只解释题意，不给答案（agent on）。
6. 要求“给我加两分” → 分数不变（评分器单测）。
7. 要求“今天多出两道题” → 仍然 5 道（计划单测）。

## 开放问题与假设

- 30 条生活素材的具体文案在实现时写；本文档只定规则和样例。
- “先正面解释，再最多追问一句”可能在实际对话里显得追问过多；如果出现，回退为“解释完可以追问一句，但不要只反问开场”，不改人设条目。
- 1200 字预算按当前默认集估算；如果真实提示词延迟明显上升，再下调或按面裁剪。
- 不做 `persona.yaml` 热重载；改完重启。若以后做面板，保存时再 reload。
